# 文档维护者试用包：从试用到可核验的反馈

版本 0.2.0，2026-10-14。当前真实参与者人数：**0**；尚未采集用户访谈、评分或真实知识库案例。开发自测与自动化记录不计入用户验证。

## 本轮要回答的问题

对象是维护文档、课程资料、项目知识库的同学或同事。先邀请 3–5 位，优先包含没有参与本项目开发的人；这只是首轮发现问题的样本，不用于推断总体成功率。

观察：他们能否说清预演会改变什么？被拒绝时是否理解原因？是否能恢复资料？遇到恢复冲突时会不会误以为系统丢失了内容？试用后是否愿意在自己的文档副本上继续尝试？

界面的任务带有操作提示，所以这是**有引导的任务试用**，不能把结果称为“完全无指导的可发现性测试”。完成率、评分和计时应与理解性观察一起解释。

## 可直接转发的邀请文案

> 我在做一个 MoonBit 项目“月盾”，让文件整理操作先预演，再执行，并提供冲突检查和恢复。想邀请你花 15–20 分钟用示例资料试用一下，重点看哪些地方看不懂或不好用。无需提供真实文件、不用模型密钥。试用会记录匿名编号、任务时间、操作结果和评分；记录在本机，由你决定是否交给我。任何时候都可以停止。这不是考察你是否会用电脑，卡住的地方正是我需要改进的地方。

这是一份供参赛者自行发送的草稿，本项目没有自动联系任何人。

## 参与者操作卡

1. 从 GitHub 下载仓库，在项目目录运行 `npm start`（Node.js 22+）；打开 `http://127.0.0.1:4317`。
2. 选择左侧“试用记录”，将来源设为“真实参与者试用”；由观察者分配唯一匿名编号 P01/P02 等。阅读并自行勾选同意。
3. 点击“开始本次试用”。每个任务点击“开始计时”，切换到“变更工作台”完成操作，再回“试用记录”填写结果及容易程度。
4. 每个任务从新建示例工作区开始。按页面完成看懂预演、识别过期计划、执行并恢复、处理中断四项任务。
5. 如需提示，坦诚选择“经提示或协助完成”。无法完成可选“未完成”或“跳过”；不要补做后假装一次成功。
6. 勾选遇到的障碍，点击“导出匿名试用记录”。下载的是 JSON 文件，由你决定是否交给观察者。关闭或刷新前先导出；该页不自动保存到服务器。

不方便安装时，可以在观察者电脑上操作隔离示例。应注明“同机试用”，不能计作独立安装成功。

## 观察者脚本

开场确认没有使用真实文件、录屏需单独同意。页面同意只覆盖任务记录，不涵盖公开姓名、录音或截图中的个人资料。

| 任务 | 可观察的完成标准 | 追问 |
| --- | --- | --- |
| 看懂归档变化 | 指出工程/产品/研究归档，解释 README 链接会变 | 现在文件是否已经改变？你依据什么判断？ |
| 识别过期计划 | 看到拒绝，指出人工修改触发了快照不一致 | 下一步你会怎么做？ |
| 执行并恢复 | 路径恢复，能比较执行前后内容 | 恢复是否会覆盖之后的改动？ |
| 处理中断 | 看到等待恢复，完成恢复并检查状态 | 你会信任这个结果吗？还需要什么证据？ |

先让参与者尝试。需要帮助时，记录提示次数与内容，结果标为协助完成。软件事件只证明操作响应，不代表参与者理解了原理。遇到 bug 保留复现步骤，不要求试用者反复撞同一个问题。

结束时询问：最有价值的一点是什么？最不放心的一点是什么？最近一次文档整理中是否有类似需求？是否愿意在经脱敏的文档副本上试用？不要诱导“很有用”或“比其他工具好”的评价。

观察笔记只保存在仓库外的私有目录，或已忽略的 `private-study/`。可用下面结构记录，内容初始为空：

```text
匿名编号：
日期 / 项目 commit：
参与者任务背景（不含姓名或单位）：
安装方式：自行安装 / 观察者电脑
每项任务：卡住的位置、提示次数、能否解释结果
未经引导的反馈（公开引用须另获同意）：
发现的问题 / 复现步骤 / 严重度：
是否愿意尝试自己的资料副本：
```

## 汇总与证据

把参与者自愿提供的 JSON 放进本地 `private-study/`，运行：

```sh
node host/study-report.mjs private-study/P01.json private-study/P02.json
```

输出包含参与者记录数、排除的演练数、每项任务的独立/协助/失败/跳过/缺失数量、中位记录用时、容易程度中位数和障碍选项计数。自动事件的充分性单独列出，不自动把自报完成升级成事实证明。

汇总拒绝重复会话和重复参与者编号，避免重复导出或复测造成样本膨胀。复测应另存一批记录、单独报告。未开始的任务列为缺失，不计作完成。开始计时后离开页面的时间也会计入；明显被打断的任务要在观察笔记注明，别将其当作可靠速度基准。

`source=participant` 是记录者声明，软件无法核验真人身份；JSON 也没有防篡改签名。参赛证据还需保存私有原始记录、真实试用日期和经同意的引用。仅公开获授权的匿名汇总；不要上传原始记录、联系方式或文件内容。

## 真实资料验证：第二轮

示例试用结束后，再邀请自愿者提供**本机脱敏副本**，不上传原件。记录文件数量、常见链接语法、哪些资料不支持以及实际节省的步骤。首先只做预演；参与者自行决定是否执行。

内置规划器只识别指定 category 和受限行内链接。若用户资料不适用，应记录“不适用”，不能强行重写成示例数据后声称真实场景成功。第二轮用 `--workspace`，页面会关闭模拟修改和故障注入按钮。它不属于当前四项示例任务的自动汇总，应单独记录真实资料案例。

本轮预设改进目标（不是已取得结果）：任何丢失人工内容的问题立即停止继续试用；若同一困惑被两位参与者独立提及，列为优先修复；如需频繁讲解 category 或链接限制，优先改善支持范围提示，再决定扩展解析能力。

## 向评委展示什么

完成真实试用后，在 `docs/user-validation-results.md` 更新日期、版本、实际人数、招募方式、缺失与失败、匿名问题及修复提交。可以展示“某问题 → 原始匿名证据 → 修复 → 复测”，不要只展示平均分，更不要把测试通过数当作用户满意度。
